# Відповідальне використання LLM під час розроблення

Велика мовна модель (LLM) може пояснювати поняття, перевіряти задум алгоритму, пропонувати код і тести або нагадувати команди Git. Вона не доводить правильність власної відповіді й не несе відповідальності за поданий результат — це робить студент.

## 1. Доречні ролі LLM

### Режим навчання

Просіть пояснювати крок за кроком, ставити діагностичні запитання й не показувати повного розв’язання одразу:

```text
Поясни українською, як flag.FlagSet підтримує підкоманди в Go.
Спочатку постав мені три запитання. Не пиши повної програми,
доки я не сформулюю власну схему обробки аргументів.
```

### Уточнення алгоритму

Спочатку самостійно сформулюйте умову, вхід, вихід, обмеження та псевдокод. LLM може шукати пропущені випадки, але не повинна непомітно змінювати умову.

### Генерування коду за специфікацією

Просіть реалізувати вже описаний алгоритм. Укажіть версію мови, дозволені пакети, сигнатури й очікувану обробку помилок. Перегляньте кожен рядок перед використанням.

### Генерування тестів

Надайте контракт і статичні тестові дані з очікуваними результатами. Попросіть не обчислювати `want` тією самою функцією, яку перевіряє тест.

### Допомога з Git

LLM може пояснити команду або скласти послідовність за виводом `git status`. Перед виконанням перевірте поточний каталог, назви файлів і наслідки кожної команди. Не виконуйте руйнівної команди, якої не розумієте.

## 2. Будова якісного запиту

Корисний запит містить:

1. **Контекст:** що це за програма і який етап роботи.
2. **Мету:** один перевірюваний результат.
3. **Умови:** формати даних, обмеження, крайні випадки.
4. **Власний задум:** алгоритм, псевдокод або ваша спроба.
5. **Обмеження:** стандартна бібліотека чи дозволена залежність.
6. **Формат відповіді:** пояснення, diff, функція або таблиця тестів.
7. **Перевірку:** команди та очікуваний результат.

Слабкий запит: `Зроби третю лабораторну на Go.`

Кращий запит:

```text
Я розширюю власну консольну програму Go. Ось контракт функції та мій
псевдокод: [...]. Запропонуй реалізацію лише цієї функції стандартною
бібліотекою. Не змінюй назви типів. Поверни код, пояснення складності
і таблицю з шістьма тестами на моєму статичному наборі [...]. Окремо
вкажи припущення, яких немає в умові.
```

## 3. Рекомендований цикл

1. Перепишіть умову своїми словами.
2. Визначте структури, поля, інваріанти й сигнатури.
3. Складіть алгоритм або псевдокод.
4. Попросіть LLM перевірити задум і поставити уточнювальні запитання.
5. Виправте специфікацію самостійно.
6. За потреби попросіть фрагмент коду, а не весь проєкт.
7. Прочитайте diff і поясніть кожну зміну.
8. Запустіть `gofmt`, `go test ./...`, `go vet ./...` і ручний сценарій.
9. Зафіксуйте суттєву взаємодію в журналі.

Якщо ви не можете пояснити запропоновану функцію, не включайте її до роботи до з’ясування.

## 4. Проєктування структури разом із LLM

Не просіть одразу видати набір полів. Надайте операції та власний начерк:

```text
Для мого варіанта треба фільтрувати за [...], сортувати за [...]
і обчислювати [...]. Я пропоную структуру з полями [...].
Постав запитання, які допоможуть знайти відсутні або надлишкові поля.
Не пропонуй фінальну структуру, доки я не відповім.
```

Після діалогу самостійно обґрунтуйте кожне поле: джерело даних, допустимі значення та операції, які його використовують.

## 5. Запит на тести

```text
Створи табличні тести Go для наведеної функції. Використай тільки цей
статичний набір: [...]. Я вручну визначив очікування: [...]. Додай
звичайний, межовий і помилковий випадки. Не використовуй випадкові
дані, зовнішні сервіси й поточний час. Поясни, яку помилку здатний
виявити кожен сценарій.
```

Звірте `want` вручну. Потім навмисно внесіть малу помилку в реалізацію: тест повинен її виявити. Після перевірки поверніть правильний код.

## 6. Запит про Git

```text
Я перебуваю в корені навчального репозиторію. Ось вивід git status:
[...]. Хочу додати до staging лише файли [...], переглянути staged diff
і створити комміт. Запропонуй команди по одній та поясни параметри.
Не використовуй reset --hard, clean або force push.
```

Команди вводьте вручну. Після кожного кроку перевіряйте `git status`, а перед коммітом — `git diff --staged`.

## 7. Онлайн-чат і агентний інструмент

Онлайн-чат доречний для пояснень, планування й навчального діалогу. Агентний інструмент може змінювати файли та запускати команди, тому явно задайте:

- дозволений каталог і конкретну частину завдання;
- команди, які можна запускати;
- заборону публікувати, видаляти чи перезаписувати дані без підтвердження;
- обов’язкове подання diff і результатів перевірки.

Не надавайте агенту реальні секрети, персональні дані або доступ до систем поза навчальною задачею. Студент сам переглядає всі зміни.

## 8. Конфіденційність і безпека

Не вставляйте в запит:

- паролі, токени, приватні ключі та вміст `.env`;
- персональні дані;
- закритий код, який не дозволено передавати сервісу;
- дані сторонніх систем без дозволу.

Використовуйте заповнювачі: `example-token`, `student-001`, `user@example.com`. Перед публікацією перегляньте `git diff --staged` і `.gitignore`. Якщо секрет уже потрапив до історії або онлайн-сервісу, вважайте його скомпрометованим і відкличте.

## 9. Перевірка відповіді

- Чи відповідає результат саме умові?
- Які припущення модель додала самостійно?
- Чи існують названі функції, пакети та параметри?
- Чи оброблено помилки та межові випадки?
- Чи не з’явилася зайва залежність?
- Чи тести справді здатні впасти через дефект?
- Чи немає секретів, небезпечної команди або небажаної зміни?
- Чи можу я пояснити рішення без LLM?

Офіційна документація, ручний розрахунок і виконуваний тест мають більшу доказову силу, ніж упевнене формулювання моделі.

## 10. Журнал використання LLM

| Поле | Що записати |
|---|---|
| сервіс / інструмент | назва використаного засобу |
| модель | назва, якщо відома |
| дата | дата взаємодії |
| мета | яку проблему розв’язували |
| стислий зміст запиту | умова й обмеження, без секретів |
| отриманий результат | пояснення, код, тест або команди |
| власні зміни | що виправлено чи відхилено |
| перевірка | тести, документація, ручний розрахунок |

Не потрібно додавати повну історію несуттєвого діалогу. Не додавайте токени доступу або персональні дані.

## 11. Коли відповідь треба відхилити

- модель не може пояснити, звідки взяла вимогу;
- код не компілюється або тест не відтворюється;
- пропонується приховати помилку чи вимкнути захист;
- команда видаляє історію або файли без необхідності;
- відповідь радить опублікувати секрет;
- рішення складніше за умову і ви не можете його захистити.

## Контрольний список

- [ ] я сам сформулював умову й алгоритм;
- [ ] запит не містив секретів або персональних даних;
- [ ] я переглянув і зрозумів кожну прийняту зміну;
- [ ] факти перевірено за документацією;
- [ ] код відформатовано, тести й аналіз пройдено;
- [ ] Git-команди виконано усвідомлено;
- [ ] суттєве використання LLM відображено у звіті;
- [ ] я можу пояснити рішення та змінити його на захисті.
