# Аргументи командного рядка та підкоманди в Go

Ця інструкція допомагає перетворити програму з інтерактивним введенням на передбачуваний інструмент командного рядка (CLI). Вона не задає предметну модель лабораторної: назви структур, поля й правила обробки студент проєктує самостійно.

## Очікуваний результат

Після опрацювання матеріалу ви зможете:

- прочитати аргументи з `os.Args`;
- описати прапорці через стандартний пакет `flag`;
- організувати кілька підкоманд за допомогою `flag.FlagSet`;
- відрізнити відсутній обов’язковий параметр від його нульового значення;
- розділити діагностичні повідомлення (`stderr`) і звичайний результат (`stdout`);
- перевірити CLI без запуску окремого процесу.

## 1. Що отримує програма

`os.Args` — зріз рядків. Перший елемент містить ім’я виконуваного файла, решта — введені користувачем аргументи:

```go
func main() {
	for index, argument := range os.Args {
		fmt.Printf("%d: %q\n", index, argument)
	}
}
```

Команда:

```text
go run . convert -value 2.5 -from m -to cm
```

передає програмі приблизно такий набір: `convert`, `-value`, `2.5`, `-from`, `m`, `-to`, `cm`. Оболонка розбирає лапки до запуску програми, тому значення з пробілами треба брати в лапки.

## 2. Підкоманда і прапорці

Зручний інтерфейс має форму:

```text
program <command> [flags]
```

Наприклад, `convert` — підкоманда, а `-value` — прапорець. Для кожної підкоманди можна створити власний `flag.FlagSet`:

```go
func run(args []string, stdout, stderr io.Writer) int {
	if len(args) == 0 {
		fmt.Fprintln(stderr, "потрібно вказати підкоманду")
		return 2
	}

	switch args[0] {
	case "convert":
		return runConvert(args[1:], stdout, stderr)
	case "help", "-h", "--help":
		printUsage(stdout)
		return 0
	default:
		fmt.Fprintf(stderr, "невідома підкоманда: %s\n", args[0])
		return 2
	}
}
```

`run` приймає аргументи й потоки явно. Завдяки цьому `main` залишається коротким, а поведінку можна тестувати через `bytes.Buffer`.

## 3. Окремий `FlagSet`

```go
func runConvert(args []string, stdout, stderr io.Writer) int {
	flags := flag.NewFlagSet("convert", flag.ContinueOnError)
	flags.SetOutput(stderr)

	value := flags.Float64("value", 0, "числове значення")
	from := flags.String("from", "", "початкова одиниця")
	to := flags.String("to", "", "цільова одиниця")

	if err := flags.Parse(args); err != nil {
		return 2
	}
	// Далі: перевірка обов'язкових параметрів і виклик логіки.
	return 0
}
```

`flag.ContinueOnError` повертає помилку замість негайного завершення процесу. Це важливо для тестів. Не використовуйте всередині `run` функції `log.Fatal` чи `os.Exit`: вони переривають увесь тестовий процес.

## 4. Обов’язкові параметри

Стандартний пакет `flag` не має окремої декларації «required». Перевірку треба виконати після `Parse`.

Для рядка часто достатньо перевірки `value == ""`. Для числа це не завжди правильно: нуль може бути допустимим значенням. Щоб з’ясувати, чи користувач явно задав прапорець, використайте `Visit`:

```go
provided := make(map[string]bool)
flags.Visit(func(item *flag.Flag) {
	provided[item.Name] = true
})

if !provided["value"] {
	fmt.Fprintln(stderr, "параметр -value є обов'язковим")
	return 2
}
```

Після перевірки наявності окремо перевірте допустимість значення: діапазон, перелік дозволених значень, взаємну сумісність параметрів.

## 5. Залишкові аргументи

Після `flags.Parse(args)` метод `flags.Args()` повертає позиційні аргументи, які не були прочитані як прапорці. Якщо команда їх не підтримує, не ігноруйте їх мовчки:

```go
if flags.NArg() != 0 {
	fmt.Fprintf(stderr, "зайві аргументи: %v\n", flags.Args())
	return 2
}
```

Подвійний дефіс `--` завершує розбір прапорців. Наступні значення вважаються позиційними, навіть якщо починаються з `-`.

## 6. Довідка та коди завершення

Визначте єдине правило:

- код `0` — команду виконано успішно;
- код `2` — помилка використання CLI: невідома команда, відсутній або некоректний параметр;
- код `1` — помилка виконання, якщо команда була коректна, але операція не вдалася.

Звичайний результат пишіть у `stdout`, повідомлення про помилки — у `stderr`. Довідка має показувати синтаксис, перелік команд, обов’язкові прапорці й хоча б один приклад.

```go
func main() {
	os.Exit(run(os.Args[1:], os.Stdout, os.Stderr))
}
```

`main` тут лише під’єднує програму до операційної системи.

## 7. Як перевіряти CLI

```go
func TestRunRequiresCommand(t *testing.T) {
	var stdout bytes.Buffer
	var stderr bytes.Buffer

	code := run(nil, &stdout, &stderr)

	if code != 2 {
		t.Fatalf("код = %d, очікується 2", code)
	}
	if !strings.Contains(stderr.String(), "підкоманду") {
		t.Fatalf("неочікуване повідомлення: %q", stderr.String())
	}
}
```

Мінімально перевірте: правильний виклик, відсутню команду, невідому команду, пропущений обов’язковий прапорець, некоректний формат числа, недопустиме значення і зайвий аргумент.

## 8. Типові помилки

- Розбір усіх підкоманд одним глобальним набором прапорців — ускладнює довідку й перевірку.
- Виклик `os.Exit` глибоко в коді — робить модульні тести незручними.
- Змішування обчислень і форматування — змушує тестувати логіку через текст.
- Перевірка числа через `!= 0` — помилково забороняє коректний нуль.
- Ігнорування помилки `Parse` або залишкових аргументів — приховує помилки користувача.
- Виведення секретів у командному рядку — аргументи можуть потрапити до історії оболонки або списку процесів.

## Практика

Запустіть і дослідіть нейтральний приклад із підкомандами: [`flag-subcommands`](../../examples/flag-subcommands/). Потім намалюйте власну таблицю: підкоманда → обов’язкові прапорці → необов’язкові прапорці → результат → помилки. Лише після цього реалізуйте інтерфейс лабораторної.

## Режими та явно передані прапорці

Для режиму, який читає дані з файла, прапорець генерації може бути забороненим навіть зі значенням `0`. Після успішного `Parse` зберіть `provided` через `Visit`, як показано вище, і перевіряйте присутність, а потім значення. Фрагмент усередині функції CLI з оголошеними `mode`, `provided` і `stderr`:

```go
if *mode == "offline" && provided["seed"] {
    fmt.Fprintln(stderr, "прапорець seed несумісний із режимом offline")
    return 2
}
```

Спочатку відхиліть невідомий режим, зайві позиційні аргументи й несумісні параметри; лише потім відкривайте файли. Явний порожній шлях має спричиняти помилку, а не непомітну підстановку типового значення. Довідку `flag.ErrHelp` обробляйте окремо як успішний запит, а не помилку використання.

Для перевірки точного коду завершення зберіть приклад. Із каталогу `examples`, PowerShell:

```powershell
go build -o flag-demo.exe ./flag-subcommands
./flag-demo.exe unknown
$LASTEXITCODE
```

Bash:

```bash
go build -o flag-demo ./flag-subcommands
./flag-demo unknown
printf '%s\n' "$?"
```

Для невідомої команди очікується `2`. `go run` має власний код завершення, тому не замінює цю перевірку. Зібраний файл після експерименту можна видалити. У модульних тестах окремо перевірте пропущений прапорець, явно переданий нуль, заборонений прапорець і порожній шлях.

Попросіть онлайн-LLM перевірити вашу таблицю сумісності параметрів, знайдіть контрприклад до її пропозиції та підтвердьте поведінку тестом. Правила журналу й агентної роботи — у [рекомендаціях щодо LLM](../llm-assisted-development/).
