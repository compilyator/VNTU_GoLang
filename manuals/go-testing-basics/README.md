# Основи тестування програм Go

Мета цієї інструкції — навчити перевіряти програму відтворювано, а не доводити її працездатність одним успішним запуском. Для лабораторної роботи перевагу слід надавати статичному набору даних. Генератор із фіксованим початковим значенням (`seed`) допустимий лише тоді, коли він справді потрібний.

**Передумови:** ви вже вмієте оголошувати функції, користуватися зрізами, циклами й умовами. Потрібні Go та текстовий редактор, наприклад VS Code. Приклади використовують стандартну бібліотеку; додаткові бібліотеки тестування встановлювати не потрібно. Команди першого прикладу підходять для PowerShell, cmd.exe та Bash на Windows, Linux і macOS.

Після опрацювання ви зможете створити тестовий файл, пояснити кожний етап тесту, запустити потрібну перевірку та зрозуміти причину її падіння. Почніть із розділів 1–2: решта інструкції розвиває цей самий спосіб мислення для різних даних і результатів.

## 1. Перший тест: навіщо він потрібний і як Go його знаходить

### Від ручної перевірки до автоматичної

Припустімо, функція додає числа. Ви можете запустити програму, ввести `4`, `-1`, `7` і переконатися, що на екрані з’явилося `10`. Але після зміни коду доведеться повторювати перевірку й пам’ятати правильну відповідь. Автоматичний тест зберігає і вхідні дані, і очікування, і правило порівняння. Команда запускає цю перевірку стільки разів, скільки потрібно.

Модульний тест перевіряє невелику одиницю поведінки, наприклад результат функції. Якщо програма компілюється, це ще не означає, що вона правильно додає числа: компілятор прийме і випадкове віднімання замість додавання. Саме зміст результату перевіряє тест. Водночас один успішний тест підтверджує лише вибраний сценарій, а не правильність програми для всіх можливих даних.

### Створіть невеликий пакет

У власному навчальному каталозі виконайте:

```text
mkdir testing-demo
cd testing-demo
go mod init example.com/testing-demo
```

`go mod init` створює файл `go.mod`, який визначає модуль. Це локальний навчальний приклад: адреса `example.com/testing-demo` є його ідентифікатором, а не вимогою створити сайт. Створіть у редакторі два файли поруч із `go.mod`:

```text
testing-demo/
    go.mod
    sum.go
    sum_test.go
```

У `sum.go` запишіть повну реалізацію:

```go
package calculator

// Sum повертає суму чисел; для порожнього зрізу результат дорівнює нулю.
// Навчальний приклад передбачає, що сума вміщується в тип int.
func Sum(values []int) int {
	total := 0
	for _, value := range values {
		total += value
	}
	return total
}
```

Це пакет `calculator`, а не виконувана програма, тому `func main()` тут не потрібна. Ми перевірятимемо `Sum` без клавіатурного введення й друку в консоль. Коментар визначає **контракт**: що функція приймає, що повертає та які припущення має. Очікування в тесті мають випливати з цього контракту.

### Правила файлів і назв

Go знаходить звичайні тести за домовленостями про імена та сигнатуру — окремо реєструвати кожний тест не потрібно. [Офіційний опис пакета testing](https://pkg.go.dev/testing) визначає ці правила.

| Елемент | Приклад | Що він означає |
|---|---|---|
| Файл реалізації | `sum.go` | Звичайний код пакета |
| Файл тестів | `sum_test.go` | Суфікс саме `_test.go`; `sum_tests.go` не підходить |
| Оголошення пакета | `package calculator` | У цьому прикладі однакове в обох файлах |
| Імпорт | `import "testing"` | Доступ до стандартних засобів повідомлення результату |
| Тестова функція | `func TestSumMixedSigns(t *testing.T)` | Функція верхнього рівня без поверненого значення |

Після `Test` назву продовжуйте з великої літери: `TestSumMixedSigns` описує суму чисел різних знаків. Формальна вимога Go — перший символ після `Test` не має бути малою літерою. Назва `testSum` не є тестом для автоматичного запуску, а `Testsum` не відповідає цій вимозі. Назви файлів і функцій чутливі до регістру там, де це визначає Go.

Основа імені файла не зобов’язана збігатися з файлом реалізації, але пара `sum.go` / `sum_test.go` полегшує пошук. В одному файлі може бути кілька тестових функцій. Кожна має описувати зрозумілий сценарій: `TestSumEmpty`, `TestSumSingleValue`, а не `Test1`.

Файли `_test.go` беруть участь у тестовій збірці, але не у звичайній збірці пакета. Тому тестові перевірки не стають частиною вашої звичайної програми. Можна також оголосити окремий тестовий пакет `calculator_test` і імпортувати `calculator` через шлях модуля — тоді перевірка працює через його експортований інтерфейс. Для початку використаємо однакове ім’я пакета: так не потрібен додатковий імпорт власного коду.

### Хто викликає тест і що таке t

Під час `go test` інструмент Go збирає пакет разом із тестами, створює тестову програму й запускає знайдені перевірки. Вам не потрібно викликати `TestSumMixedSigns` із `main` або вручну створювати `testing.T`.

Параметр `t *testing.T` надає поточному тесту засоби запису діагностики та повідомлення про збій. Ім’я `t` — звична коротка назва параметра. Якщо тест просто викликав `Sum` і завершився без повідомлення про помилку, він може пройти навіть за неправильного результату. Тому наступний розділ додає явну перевірку.

## 2. Arrange — Act — Assert: один тест від початку до кінця

AAA — спосіб організувати тест у три послідовні етапи: **підготовка → дія → перевірка**. Це не спеціальний синтаксис Go і не бібліотека. Поділ допомагає читачеві побачити, за яких умов виконується сценарій, що саме викликається і за яким правилом ми визнаємо результат правильним.

### Повний файл sum_test.go з поясненнями

Скопіюйте цей блок цілком у `sum_test.go`. Усі три етапи належать одному тесту; додаткового коду для його запуску не потрібно.

```go
package calculator

import "testing"

func TestSumMixedSigns(t *testing.T) {
	// ARRANGE — готуємо умови саме цього сценарію.
	// Додатні й від’ємне числа допоможуть перевірити знак доданків.
	// Дані локальні: інший тест не має їх готувати або змінювати.
	values := []int{4, -1, 7}
	// Очікування визначаємо за контрактом і рахуємо вручну:
	// 4 + (-1) + 7 = 10. Не викликаємо Sum для обчислення want,
	// інакше могли б порівняти помилкову відповідь із нею самою.
	want := 10

	// ACT — виконуємо дію, поведінку якої перевіряємо.
	// Передаємо підготовлені дані й зберігаємо фактичний результат.
	// Цей виклик не доводить правильність: він лише дає відповідь.
	got := Sum(values)

	// ASSERT — перевіряємо, чи виконано очікування.
	// Для цілих чисел у цьому прикладі потрібна точна рівність.
	// Якщо відповіді різні, повідомляємо вхід, факт і очікування.
	// Fatalf позначає тест невдалим і зупиняє поточний тест.
	if got != want {
		t.Fatalf("Sum(%v) = %d, очікується %d", values, got, want)
	}
}
```

### Arrange: які умови ми створили і чому саме такі

Підготовка відповідає на запитання: «Що має бути відомо до виклику функції?» Тут це `values` та `want`. Числа невеликі, тому правильну суму легко перевірити без допоміжної програми. Від’ємне число робить сценарій змістовнішим за перевірку лише додатних чисел.

`want` — очікувана відповідь, яку ми визначили незалежно від реалізації. Запис `want := Sum(values)` був би помилкою проєктування тесту: збій у `Sum` потрапив би і в очікування, і у фактичний результат. Копіювати цикл із реалізації в тест теж не варто — можна скопіювати ту саму помилку.

В інших задачах Arrange може створити структуру, буфер або тимчасовий файл. Але кожна така дія має пояснювати умови сценарію. Наприклад, для перевірки читання файла спочатку треба записати відомий текст; для перевірки суми файл лише ускладнив би тест.

### Act: яку поведінку ми запустили

Рядок `got := Sum(values)` є центральною дією. `got` означає фактично отриманий результат. Назви `got` і `want` — поширена домовленість, не ключові слова мови.

У нашому тесті достатньо одного виклику. Не додавайте сюди друк меню, запит до сервера чи зчитування з клавіатури: вони не потрібні для перевірки додавання. В інших сценаріях дія може складатися з кількох операцій, якщо саме їхня послідовність є предметом перевірки, наприклад запис і подальше читання. AAA не вимагає механічно обмежувати будь-який тест одним рядком.

### Assert: як тест ухвалює рішення

Умова `got != want` знаходить відхилення від контракту. Коли значення збігаються, тіло `if` пропускається й тест завершується успішно. Коли не збігаються, `t.Fatalf` передає тестовому механізму сигнал про помилку. Звичайний `fmt.Println` лише надрукував би текст і не зробив би тест невдалим.

Формат `%v` показує вхідний зріз, а `%d` — цілі числа. Наприклад, діагностика `Sum([4 -1 7]) = 12, очікується 10` одразу пояснює, який сценарій не пройшов. До повідомлення тестовий механізм додає файл і номер рядка.

`t.Errorf` теж позначає тест невдалим, але дозволяє виконувати його далі. Це зручно для незалежних перевірок кількох полів. `t.Fatalf` доречний, коли продовження не має сенсу або небезпечне, наприклад після неочікуваної помилки замість потрібного об’єкта. Він не зупиняє весь набір тестів. У нашому короткому прикладі обидва варіанти виявили б неправильну суму; обрано `Fatalf`, бо після цієї перевірки нічого робити.

Один сценарій може потребувати кількох тверджень: наприклад, відсутність помилки та правильне значення. «Один тест — одна поведінка» не означає «лише один `if`». Важливо, щоб усі перевірки стосувалися зрозумілої мети тесту.

### Запуск і читання результату

З каталогу `testing-demo`, де міститься `go.mod`, виконайте:

```text
gofmt -w sum.go sum_test.go
go test -v .
```

`gofmt` узгоджує форматування коду. Крапка в `go test` означає поточний пакет. Очікуйте назву `TestSumMixedSigns`, позначку `PASS` і підсумковий рядок `ok`; час виконання може відрізнятися. `-v` показує назви навіть успішних тестів. Без нього успішний запуск зазвичай дає стислий підсумок пакета.

Команди для подальшої роботи:

```text
go test ./...
go test -v -run "^TestSumMixedSigns$" .
go test -count=1 .
```

`./...` знаходить пакети від поточного каталогу вниз; із кореня цього простого модуля це весь приклад. `-run` відбирає назви за регулярним виразом, а `^` та `$` обмежують збіг повною назвою. Подвійні лапки в цій команді підходять і для cmd.exe. `-count=1` примушує виконати тести знову замість використання кешованого успішного результату. Позначка `(cached)` без цього параметра означає повторне використання попереднього результату, а не новий запуск тесту.

### Переконайтеся, що тест справді виявляє помилку

У власному навчальному прикладі тимчасово замініть `total += value` на `total -= value`, не змінюючи `want`. Повторіть `go test -v .`. Очікується `FAIL`: функція поверне `-10` замість `10`. Прочитайте вхідні дані, фактичний результат і номер рядка в повідомленні. Потім поверніть додавання та знову отримайте `PASS`.

Це контрольована перевірка самого тесту. Якщо після відомої помилки він залишається успішним, з’ясуйте, чи запустився потрібний тест і чи має він дієве твердження. Не підганяйте `want` під зламану реалізацію: спочатку звіряйтеся з контрактом.

Самостійно додайте `TestSumEmpty`: підготуйте порожній зріз, визначте очікування за коментарем до `Sum`, викличте функцію та порівняйте результат. Поясніть, який рядок належить кожному етапу AAA. Для підтвердження збережіть код і результати успішного запуску, контрольованого падіння та відновлення.

У робочих тестах настільки докладні коментарі не обов’язкові. Тут вони допомагають навчитися відділяти підготовку від дії та перевірки. Надалі часто достатньо порожніх рядків між етапами й пояснення причини неочевидного набору даних.

## 3. Табличні тести

Перший тест перевіряв один набір чисел. Якщо для кожного нового набору копіювати всю функцію тесту, однакові виклики й перевірки швидко займуть більшість файла. Табличний тест відділяє змінні дані сценаріїв від спільного порядку перевірки. Для `Sum` рядок таблиці міг би містити назву, зріз чисел і очікувану суму.

Нижче — інший приклад, щоб показати ту саму структуру для рядків. Фрагмент передбачає функцію `Normalize(input string) string`, яка прибирає пробіли на початку й у кінці, наприклад через `strings.TrimSpace`. Для окремого запуску додайте її реалізацію до пакета, а цей тест — до файла `normalize_test.go` з тим самим `package` та імпортом `testing`. До початкового `sum_test.go` без такої функції його додавати не слід.

```go
func TestNormalize(t *testing.T) {
	tests := []struct {
		name  string
		input string
		want  string
	}{
		{name: "spaces", input: "  hello  ", want: "hello"},
		{name: "already clean", input: "hello", want: "hello"},
		{name: "empty", input: "", want: ""},
	}

	for _, test := range tests {
		t.Run(test.name, func(t *testing.T) {
			got := Normalize(test.input)
			if got != test.want {
				t.Fatalf("Normalize(%q) = %q, очікується %q", test.input, got, test.want)
			}
		})
	}
}
```

Назва сценарію має описувати сенс випадку, а не бути `test1` чи `case2`. `t.Run` створює іменований підтест: у виведенні видно, який саме рядок таблиці не пройшов. Змінна `test` містить поточний рядок. Таблиця готує умови Arrange, виклик `Normalize` виконує Act, а `if` із `Fatalf` утворює Assert. AAA нікуди не зникає — спільний шаблон застосовується до кожного рядка.

## 4. Відтворювані дані

### Рекомендований варіант: статичний набір

```go
values := []int{8, -3, 8, 0, 15, -3}
```

Переваги: набір видно в коді, очікуваний результат можна обчислити вручну, збій легко повторити, у звіті можна показати конкретний сценарій.

### Допустимий виняток: фіксований `seed`

```go
source := rand.New(rand.NewSource(20260315))
```

Не використовуйте поточний час як `seed` в обов’язковому тесті. Якщо генератор потрібний, зафіксуйте `seed` у коді та повідомленні про помилку. Не робіть очікуваний результат другим викликом тієї самої функції, яку тестуєте.

## 5. Які сценарії добирати

Для кожної операції визначте класи вхідних даних:

- звичайний коректний випадок;
- порожній набір, якщо він дозволений;
- один елемент;
- межові значення;
- повтори;
- від’ємні, нульові та додатні числа, якщо доречно;
- неправильні параметри;
- випадок, у якому очікується помилка.

Кількість тестів сама по собі не є метою. Кожен тест має перевіряти нову суттєву властивість.

## 6. Перевірка помилок

Помилка теж є результатом, передбаченим контрактом. Якщо функція перетворює текст на число, для тексту `not-a-number` правильна поведінка — відмовити в перетворенні, а не мовчки повернути нуль як коректне значення. Наступний фрагмент слід розмістити всередині тестової функції; він передбачає наявність `ParseValue`, яка повертає значення й `error`.

```go
// Arrange: навмисно задаємо текст, який не є числом.
input := "not-a-number"
// Act: зберігаємо обидва результати виклику.
got, err := ParseValue(input)
// Assert: успіхом тесту є саме наявність очікуваної помилки.
if err == nil {
	t.Fatalf("очікувалася помилка, отримано значення %v", got)
}
```

Для коректного вводу, навпаки, спочатку перевірте `err != nil` і завершіть тест через `t.Fatalf`, якщо помилка неочікувана. Лише потім порівнюйте значення. Так діагностика покаже справжню причину збою, а не наслідок невдалого перетворення.

Якщо пакет експортує відому помилку, перевіряйте її через `errors.Is`. Не прив’язуйте тест до повного тексту помилки без потреби: формулювання може змінитися, тоді як тип або значення помилки лишається тим самим.

## 7. Числа з рухомою комою

Результати обчислень із `float64` часто не можна порівнювати оператором `==`. Використайте допустиму похибку:

```go
const epsilon = 1e-9
if math.Abs(got-want) > epsilon {
	t.Fatalf("результат = %.12f, очікується %.12f", got, want)
}
```

Значення `epsilon` має відповідати задачі; не обирайте його настільки великим, щоб тест приховував помилки.

## 8. Тестування текстового виведення

Функція, яка приймає `io.Writer`, не залежить від реальної консолі:

```go
func PrintReport(writer io.Writer, title string, value int) {
	fmt.Fprintf(writer, "%s: %d\n", title, value)
}
```

У тесті:

```go
var output bytes.Buffer
PrintReport(&output, "Усього", 3)

if got, want := output.String(), "Усього: 3\n"; got != want {
	t.Fatalf("виведення = %q, очікується %q", got, want)
}
```

Не слід перевіряти кожен пробіл у складній таблиці, якщо форматування не є частиною контракту. Логіку обчислень тестуйте окремо від подання.

## 9. Незалежність тестів

Тест має запускатися окремо, у довільному порядку й повторно. Не покладайтеся на змінну, яку змінив попередній тест. Не використовуйте реальні облікові дані чи зовнішній сервіс для модульного тесту. Якщо створюєте тимчасові файли, використовуйте `t.TempDir()`.

## 10. Що тестувати в лабораторній

Обов’язково перевірте щонайменше ключові функції предметної логіки та помилкові вхідні дані. Для CLI додайте окремі перевірки розбору аргументів. Тест не повинен повторювати реалізацію алгоритму рядок у рядок: очікування визначайте вручну на малих зрозумілих наборах.

Приклади: [`table-driven-tests`](../../examples/table-driven-tests/) і [`writer-output`](../../examples/writer-output/).

## 11. Вибір тесту та читання помилки

Для практики потрібні встановлений Go та локальна копія [навчальних прикладів](../../examples/README.md). Перейдіть у каталог `examples` цієї копії, де лежить `go.mod`. Команди нижче однакові в PowerShell і Bash. Запишіть фактичну версію через `go version`.

Запустіть наявний тест і лише його сценарій порожнього набору:

```text
go test -v -run '^TestAverage$' ./table-driven-tests
go test -v -run '^TestAverage$/^empty$' ./table-driven-tests
```

`-run` приймає регулярний вираз, а `/` розділяє рівні тесту й підтесту. `^` і `$` обмежують збіг повною назвою. У другому запуску очікується `TestAverage/empty` зі статусом `PASS`. Повідомлення `no tests to run` означає, що потрібний тест не виконався: перевірте назву та каталог.

Щоб перевірити якість самого тесту, працюйте лише у власній копії прикладу:

1. Запустіть правильну версію й переконайтеся в `PASS`.
2. У рядку таблиці `five values` тимчасово замініть `want: 30` на `want: 31`.
3. Повторіть першу команду. Очікуються `FAIL` і повідомлення `average() = 30, want 31` із файлом та номером рядка.
4. Поясніть різницю між фактичним і очікуваним: вручну обчисліть середнє п’яти значень.
5. Поверніть `want: 30` і виконайте `go test ./...`.

Не змінюйте очікування лише заради зеленого результату: спочатку звірте контракт. Зафіксуйте успішний запуск, контрольоване падіння та повторний успіх. У фінальній версії навмисної помилки бути не повинно.

## 12. Базове покриття коду

Покриття показує, які оператори виконалися під час тестів. Воно допомагає знайти неперевірені ділянки, але не підтверджує правильність очікувань або повноту перевірки умов.

Із того самого каталогу `examples` виконайте:

```text
go test -cover ./table-driven-tests
go test '-coverprofile=coverage.out' ./table-driven-tests
go tool cover '-func=coverage.out'
```

Очікуються відсоток покриття, файл `coverage.out` і таблиця функцій. Аргумент із назвою файла взято в лапки для однозначного передавання в PowerShell і Bash. Поясніть, чому `average` і `main` можуть мати різне покриття. Не додавайте тест лише заради виклику рядка: сформулюйте поведінку, яку він має перевірити. За потреби `go tool cover '-html=coverage.out'` відкриває звіт у браузері.

Після роботи видаліть тільки створений `coverage.out` із навчальної копії або збережіть його як результат перевірки; не додавайте тимчасовий файл до вихідного коду. Fuzzing, пошук гонок даних і перевірки залежності від порядку запуску потребують окремої поглибленої практики.

## 13. Робота з LLM

Для добору пропущених сценаріїв достатньо онлайн-чату. Надайте контракт функції та невеликий синтетичний набір і попросіть запропонувати звичайні, межові й помилкові випадки. Самостійно визначте очікування, відкиньте дублікати й перевірте, що прийняті тести здатні виявляти помилку.

Агентний інструмент доречний для редагування тестів і запуску команд лише у власній копії навчального прикладу. Перегляньте diff; не дозволяйте змінювати контракт або видаляти перевірки, щоб приховати падіння. Результат LLM підтверджується виконанням тесту й ручним розрахунком.

У [журналі використання LLM](../llm-assisted-development/README.md) запишіть сервіс чи інструмент, модель за наявності, дату, мету, істотний запит, використаний результат, власні зміни та спосіб перевірки. Не надавайте секрети або персональні дані.

## Типові помилки

- файл названо `sum_tests.go` або функцію названо `testSum`, тому перевірка не запускається;
- відсутні `package` чи `import "testing"` після копіювання лише частини прикладу;
- запуск `go run sum_test.go` замість `go test` або запуск команди не з потрібного модуля;
- повідомлення `[no test files]` чи `no tests to run` помилково сприйнято як підтвердження перевірки: перевірте файл, ім’я, каталог і фільтр `-run`;
- замість `t.Errorf` або `t.Fatalf` використано лише друк діагностики, який не позначає тест невдалим;
- випадкові дані без фіксованого `seed`;
- лише один «щасливий» сценарій;
- тест без перевірки результату;
- обчислення `want` тим самим алгоритмом, що й `got`;
- залежність тесту від порядку запуску;
- тестування тільки `main`, коли предметна логіка не винесена у функції;
- приховування корисного повідомлення через загальне `тест не пройдено`.

## Файли, JSON і HTML у тестах

Для файлових тестів використовуйте `t.TempDir()` і `filepath.Join`: кожен тест отримує окремий каталог, який прибирає тестовий інструмент. Не перевіряйте запис на власних робочих документах.

| Сценарій | Що перевіряти |
| --- | --- |
| Збереження й відновлення JSON | Значення, порядок і повтори; не тільки відсутність помилки |
| Наявний вихідний файл | Помилка та незмінений початковий вміст |
| Межа читання | Рівно межа приймається, межа плюс один байт відхиляється |
| Некоректний JSON | Невідоме поле, другий документ, неправильний тип, пропущене значення |
| HTML | Очікувані показники та екранований недовірений текст |
| Помилка шаблону | Вихідний файл не створено |
| Час | Фіксований параметр замість залежності від поточного годинника |

Виконувані зразки: [файли](../../examples/file-safety/main_test.go), [JSON](../../examples/json-strict/main_test.go), [HTML](../../examples/html-report/main_test.go). HTML-тест підставляє нешкідливий навчальний рядок із тегом і перевіряє, що він став текстом. Працюйте лише з локальним навчальним звітом. Цей тест не замінює перегляд довіреного шаблону, CSS та скриптів.

Порівняння цілого HTML крихке до змін оформлення. Перевіряйте важливі дані й екранування, а вузький екран, друк і читабельність перевіряйте в браузері. Час передавайте у функцію побудови моделі, як у `buildReport(data, now)`.

Практика: попросіть онлайн-LLM запропонувати пропущений негативний сценарій, поясніть його очікування й реалізуйте тест самостійно. Агенту дозволяйте змінювати лише копію прикладу; перегляньте diff, повторіть тести та заповніть [журнал використання LLM](../llm-assisted-development/).

## Самоперевірка

1. Чому статичний набір даних кращий для першого тесту?
2. Коли потрібний `-count=1`?
3. Чим табличний тест відрізняється від кількох копій майже однакового коду?
4. Чому не варто порівнювати всі `float64` через `==`?
5. Як перевірити консольне виведення без ручного запуску програми?
6. Чому `sum_test.go` розпізнається як тестовий файл, а `sum_tests.go` — ні?
7. Хто викликає `TestSumMixedSigns` і звідки береться `t *testing.T`?
8. Які рядки повного тесту належать Arrange, Act і Assert? Що втратить тест без останнього етапу?
9. Чому `want := Sum(values)` не є незалежною перевіркою?
10. Коли варто завершити поточний тест через `Fatalf`, а коли можна продовжити після `Errorf`?
