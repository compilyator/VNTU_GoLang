# Основи тестування програм Go

Мета цієї інструкції — навчити перевіряти програму відтворювано, а не доводити її працездатність одним успішним запуском. Для лабораторної роботи перевагу слід надавати статичному набору даних. Генератор із фіксованим початковим значенням (`seed`) допустимий лише тоді, коли він справді потрібний.

## 1. Перший тест

Тестовий файл має суфікс `_test.go` і зазвичай лежить поруч із кодом пакета:

```go
func TestSum(t *testing.T) {
	got := Sum([]int{4, -1, 7})
	want := 10

	if got != want {
		t.Fatalf("Sum() = %d, очікується %d", got, want)
	}
}
```

Назва тестової функції починається з `Test`, далі йде назва перевірюваної поведінки. Повідомлення про помилку має містити фактичний та очікуваний результати.

Запуск:

```text
go test ./...
go test -v ./...
go test -run TestSum ./...
go test -count=1 ./...
```

`./...` охоплює всі пакети поточного модуля. `-count=1` вимикає використання кешованого результату для цього запуску.

## 2. Arrange — Act — Assert

Зручно мислити трьома частинами:

1. **Arrange** — підготувати вхідні дані та очікування.
2. **Act** — викликати рівно ту поведінку, яку перевіряємо.
3. **Assert** — порівняти фактичний результат з очікуваним.

Не обов’язково писати ці слова в кожному тесті. Важливо, щоб структура була зрозумілою.

## 3. Табличні тести

Коли одна функція має багато сценаріїв, використовуйте таблицю:

```go
func TestNormalize(t *testing.T) {
	tests := []struct {
		name  string
		input string
		want  string
	}{
		{name: "spaces", input: "  hello  ", want: "hello"},
		{name: "already clean", input: "hello", want: "hello"},
		{name: "empty", input: "", want: ""},
	}

	for _, test := range tests {
		t.Run(test.name, func(t *testing.T) {
			got := Normalize(test.input)
			if got != test.want {
				t.Fatalf("Normalize(%q) = %q, очікується %q", test.input, got, test.want)
			}
		})
	}
}
```

Назва сценарію має описувати сенс випадку, а не бути `test1` чи `case2`.

## 4. Відтворювані дані

### Рекомендований варіант: статичний набір

```go
values := []int{8, -3, 8, 0, 15, -3}
```

Переваги: набір видно в коді, очікуваний результат можна обчислити вручну, збій легко повторити, у звіті можна показати конкретний сценарій.

### Допустимий виняток: фіксований `seed`

```go
source := rand.New(rand.NewSource(20260315))
```

Не використовуйте поточний час як `seed` в обов’язковому тесті. Якщо генератор потрібний, зафіксуйте `seed` у коді та повідомленні про помилку. Не робіть очікуваний результат другим викликом тієї самої функції, яку тестуєте.

## 5. Які сценарії добирати

Для кожної операції визначте класи вхідних даних:

- звичайний коректний випадок;
- порожній набір, якщо він дозволений;
- один елемент;
- межові значення;
- повтори;
- від’ємні, нульові та додатні числа, якщо доречно;
- неправильні параметри;
- випадок, у якому очікується помилка.

Кількість тестів сама по собі не є метою. Кожен тест має перевіряти нову суттєву властивість.

## 6. Перевірка помилок

```go
got, err := ParseValue("not-a-number")
if err == nil {
	t.Fatalf("очікувалася помилка, отримано значення %v", got)
}
```

Якщо пакет експортує відому помилку, перевіряйте її через `errors.Is`. Не прив’язуйте тест до повного тексту помилки без потреби: формулювання може змінитися, тоді як тип або значення помилки лишається тим самим.

## 7. Числа з рухомою комою

Результати обчислень із `float64` часто не можна порівнювати оператором `==`. Використайте допустиму похибку:

```go
const epsilon = 1e-9
if math.Abs(got-want) > epsilon {
	t.Fatalf("результат = %.12f, очікується %.12f", got, want)
}
```

Значення `epsilon` має відповідати задачі; не обирайте його настільки великим, щоб тест приховував помилки.

## 8. Тестування текстового виведення

Функція, яка приймає `io.Writer`, не залежить від реальної консолі:

```go
func PrintReport(writer io.Writer, title string, value int) {
	fmt.Fprintf(writer, "%s: %d\n", title, value)
}
```

У тесті:

```go
var output bytes.Buffer
PrintReport(&output, "Усього", 3)

if got, want := output.String(), "Усього: 3\n"; got != want {
	t.Fatalf("виведення = %q, очікується %q", got, want)
}
```

Не слід перевіряти кожен пробіл у складній таблиці, якщо форматування не є частиною контракту. Логіку обчислень тестуйте окремо від подання.

## 9. Незалежність тестів

Тест має запускатися окремо, у довільному порядку й повторно. Не покладайтеся на змінну, яку змінив попередній тест. Не використовуйте реальні облікові дані чи зовнішній сервіс для модульного тесту. Якщо створюєте тимчасові файли, використовуйте `t.TempDir()`.

## 10. Що тестувати в лабораторній

Обов’язково перевірте щонайменше ключові функції предметної логіки та помилкові вхідні дані. Для CLI додайте окремі перевірки розбору аргументів. Тест не повинен повторювати реалізацію алгоритму рядок у рядок: очікування визначайте вручну на малих зрозумілих наборах.

Приклади: [`table-driven-tests`](../../examples/table-driven-tests/) і [`writer-output`](../../examples/writer-output/).

## 11. Вибір тесту та читання помилки

Для практики потрібні встановлений Go та локальна копія [навчальних прикладів](../../examples/README.md). Перейдіть у каталог `examples` цієї копії, де лежить `go.mod`. Команди нижче однакові в PowerShell і Bash. Запишіть фактичну версію через `go version`.

Запустіть наявний тест і лише його сценарій порожнього набору:

```text
go test -v -run '^TestAverage$' ./table-driven-tests
go test -v -run '^TestAverage$/^empty$' ./table-driven-tests
```

`-run` приймає регулярний вираз, а `/` розділяє рівні тесту й підтесту. `^` і `$` обмежують збіг повною назвою. У другому запуску очікується `TestAverage/empty` зі статусом `PASS`. Повідомлення `no tests to run` означає, що потрібний тест не виконався: перевірте назву та каталог.

Щоб перевірити якість самого тесту, працюйте лише у власній копії прикладу:

1. Запустіть правильну версію й переконайтеся в `PASS`.
2. У рядку таблиці `five values` тимчасово замініть `want: 30` на `want: 31`.
3. Повторіть першу команду. Очікуються `FAIL` і повідомлення `average() = 30, want 31` із файлом та номером рядка.
4. Поясніть різницю між фактичним і очікуваним: вручну обчисліть середнє п’яти значень.
5. Поверніть `want: 30` і виконайте `go test ./...`.

Не змінюйте очікування лише заради зеленого результату: спочатку звірте контракт. Зафіксуйте успішний запуск, контрольоване падіння та повторний успіх. У фінальній версії навмисної помилки бути не повинно.

## 12. Базове покриття коду

Покриття показує, які оператори виконалися під час тестів. Воно допомагає знайти неперевірені ділянки, але не підтверджує правильність очікувань або повноту перевірки умов.

Із того самого каталогу `examples` виконайте:

```text
go test -cover ./table-driven-tests
go test '-coverprofile=coverage.out' ./table-driven-tests
go tool cover '-func=coverage.out'
```

Очікуються відсоток покриття, файл `coverage.out` і таблиця функцій. Аргумент із назвою файла взято в лапки для однозначного передавання в PowerShell і Bash. Поясніть, чому `average` і `main` можуть мати різне покриття. Не додавайте тест лише заради виклику рядка: сформулюйте поведінку, яку він має перевірити. За потреби `go tool cover '-html=coverage.out'` відкриває звіт у браузері.

Після роботи видаліть тільки створений `coverage.out` із навчальної копії або збережіть його як результат перевірки; не додавайте тимчасовий файл до вихідного коду. Fuzzing, пошук гонок даних і перевірки залежності від порядку запуску потребують окремої поглибленої практики.

## 13. Робота з LLM

Для добору пропущених сценаріїв достатньо онлайн-чату. Надайте контракт функції та невеликий синтетичний набір і попросіть запропонувати звичайні, межові й помилкові випадки. Самостійно визначте очікування, відкиньте дублікати й перевірте, що прийняті тести здатні виявляти помилку.

Агентний інструмент доречний для редагування тестів і запуску команд лише у власній копії навчального прикладу. Перегляньте diff; не дозволяйте змінювати контракт або видаляти перевірки, щоб приховати падіння. Результат LLM підтверджується виконанням тесту й ручним розрахунком.

У [журналі використання LLM](../llm-assisted-development/README.md) запишіть сервіс чи інструмент, модель за наявності, дату, мету, істотний запит, використаний результат, власні зміни та спосіб перевірки. Не надавайте секрети або персональні дані.

## Типові помилки

- випадкові дані без фіксованого `seed`;
- лише один «щасливий» сценарій;
- тест без перевірки результату;
- обчислення `want` тим самим алгоритмом, що й `got`;
- залежність тесту від порядку запуску;
- тестування тільки `main`, коли предметна логіка не винесена у функції;
- приховування корисного повідомлення через загальне `тест не пройдено`.

## Самоперевірка

1. Чому статичний набір даних кращий для першого тесту?
2. Коли потрібний `-count=1`?
3. Чим табличний тест відрізняється від кількох копій майже однакового коду?
4. Чому не варто порівнювати всі `float64` через `==`?
5. Як перевірити консольне виведення без ручного запуску програми?
