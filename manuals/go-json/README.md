# JSON у Go: формат, перевірка та відновлення даних

**Мета:** визначити невеликий формат збереження й відхиляти дані, що порушують його контракт. **Передумови:** структури, вказівники, помилки та [файли й потоки](../go-files-io/). **Середовище:** Go 1.25, Windows / PowerShell або Linux/macOS / Bash; сторонніх бібліотек немає. Використовуємо стандартний `encoding/json` цієї версії.

Очікуваний результат — функція читання, яка повертає перевірену структуру або зрозумілу помилку, і тест збереження та відновлення значень.

## 1. Визначте контракт

[Приклад `json-strict`](../../examples/json-strict/) описує одну позицію запасів:

```json
{"version":1,"name":"Кабель","quantity":0}
```

Версія — лише `1`, назва — непорожня, кількість — ціле число від 0 до 100. Усі поля обов’язкові; один документ має займати не більше 1024 байтів разом із кінцевими пробілами. Це навчальні обмеження прикладу, а не предметні вимоги лабораторної.

## 2. Опишіть структуру

Експортовані поля Go доступні декодеру; тег `json:"quantity"` задає назву в JSON. Поле `Quantity *int` дозволяє відрізнити число `0` від відсутнього поля або `null`. Для нового значення структури обидва останні випадки дають `nil` і тут відхиляються. Вказівник сам собою не розрізняє відсутність і `null`; якщо це потрібно, необхідний додатковий облік присутності.

Не додавайте `omitempty` механічно: для звичайного числа воно може прибрати важливий нуль при збереженні. Назви полів та одиниці вимірювання мають бути узгоджені між записом і читанням.

## 3. Перевіряйте послідовно

1. Прочитайте не більше межі плюс один байт і відхиліть перевищення.
2. Створіть `json.Decoder`, увімкніть `DisallowUnknownFields` і виконайте `Decode`.
3. Виконайте другий `Decode`: лише `io.EOF` означає, що залишилися самі пробіли. Успішне друге декодування означає зайвий документ; інша помилка — сторонні або пошкоджені дані.
4. Перевірте версію, обов’язкові значення й предметні діапазони.

Успішний синтаксичний розбір не гарантує коректності предметних даних. Застосовуйте однакові предметні правила до завантажених і згенерованих значень.

**Межі прикладу:** `DisallowUnknownFields` не відхиляє повторювані ключі й не забезпечує точний регістр імен полів у `encoding/json` Go 1.25. Приклад не реалізує окремий контроль цих випадків і не є універсальним валідатором JSON. Для суворішого протоколу потрібні додаткові правила та перевірки.

## 4. Збережіть і відновіть

`json.MarshalIndent` формує читабельні байти JSON; перевірте його помилку до створення файла. Для запису використайте підхід із [прикладу файлових операцій](../../examples/file-safety/). Для малого набору буферизація спрощує відмову без неповного файла.

Зберігайте вихідні значення, порядок і повтори. Похідні показники обчислюйте повторно після читання; порівнюйте значення, а не пробіли у JSON. Якщо додаєте необов’язковий seed, нуль може бути справжнім значенням — врахуйте присутність поля.

Час отримання даних і час створення звіту — різні факти. Для часу з часовим поясом можна використати `time.Parse(time.RFC3339, value)`; при повторному аналізі первинний час не замінюють поточним. Для власних числових моделей також перевіряйте допустимість значень до серіалізації.

## 5. Запуск

Із каталогу `examples`, PowerShell або Bash:

```text
go run ./json-strict
go test -v ./json-strict
```

Програма друкує форматований документ з версією 1, назвою «Кабель» і кількістю 0. Тести перевіряють неправильний тип, пропущене поле, `null`, зайве поле, другу структуру, сторонній текст, діапазони й межу байтів. Окрема перевірка відновлює серіалізоване значення й порівнює його з оригіналом.

## Практика та LLM

До запуску складіть таблицю «вхід → очікуване прийняття або причина відмови». Додайте випадки кількості 100, 101 і пробілів після документа; зіставте прогноз із тестом. Для практики порядку й повторів спроєктуйте власний масив позицій та перевірте збереження двох однакових елементів.

Попросіть онлайн-LLM запропонувати негативні випадки для описаного контракту, пояснюючи кожен. Перевірте їх самостійно: модель може помилково стверджувати, що стандартний декодер забороняє дублікати ключів. Для написання тестів агентом обмежте роботу власною копією прикладу, перегляньте diff і повторіть запуск. У журналі зазначте сервіс, модель, якщо відома, дату, мету, запити, прийнятий результат, власні зміни та перевірки. Реальні дані й секрети не потрібні.

## Типові проблеми й самоперевірка

- Число у лапках — рядок, тому не відповідає `int`.
- Другий документ прийнято — перевіряється лише перший `Decode`.
- Пропущена кількість стала нулем — вхідна модель не зберігає присутність поля.
- Валідний JSON має неправильний зміст — пропущено предметну перевірку.

Чому `json.Valid` недостатньо? Навіщо версія формату? Чому тест відновлення має перевіряти значення, а не лише відсутність помилки?
