# Структура невеликого консольного проєкту Go

Ця інструкція показує, як розділити невелику програму на пакети так, щоб `main.go` лишався простим, а предметну логіку можна було перевіряти незалежно від консолі. Наведені назви нейтральні: структури та поля для свого варіанта студент визначає сам.

## 1. Головний принцип

`main` — точка складання програми, а не місце для всієї логіки. Він має:

1. отримати залежності операційної системи (`os.Args`, `os.Stdin`, `os.Stdout`, `os.Stderr`);
2. передати їх функції застосунку;
3. повернути код завершення.

```go
func main() {
	os.Exit(run(os.Args[1:], os.Stdin, os.Stdout, os.Stderr))
}
```

Якщо в `main` одночасно читаються дані, сортується зріз, обчислюється статистика й малюється таблиця, компоненти надто тісно пов’язані.

## 2. Приклад структури

```text
project/
├── go.mod
├── main.go
├── domain/
│   ├── record.go
│   └── record_test.go
├── analysis/
│   ├── analysis.go
│   └── analysis_test.go
└── console/
    ├── input.go
    ├── output.go
    └── output_test.go
```

Це не обов’язковий шаблон. Для малої програми двох пакетів достатньо; не створюйте каталог для кожної функції. Межа пакета виправдана, коли група коду має окрему відповідальність.

## 3. Відповідальності

- `domain` — предметні типи, їхні інваріанти та прості операції.
- `analysis` — алгоритми обробки колекцій і обчислення результатів.
- `console` — читання введення, розбір тексту, форматування результату.
- `main` — з’єднання компонентів.

Напрям залежностей бажано будувати від зовнішнього шару до внутрішнього: `main` імпортує `console` й предметні пакети; консоль може використовувати предметні типи; предметна логіка не повинна імпортувати консоль.

## 4. Як проєктувати власну структуру

Не починайте з випадкового переліку полів. Для свого варіанта дайте відповіді:

1. Який об’єкт описує один елемент набору?
2. Які дані є його властивостями, а які можна обчислити?
3. Які поля потрібні для фільтрації, сортування, пошуку й подання?
4. Які значення заборонені або взаємопов’язані?
5. Чи має одиниця вимірювання бути частиною поля, окремим полем або правилом типу?

```go
type Record struct {
	Name     string
	Category string
	Value    float64
}
```

Це лише приклад форми, не готова модель лабораторної. Назви й типи мають випливати з вашої предметної області.

## 5. Інваріанти та конструктор

Інваріант — умова, що має бути істинною для кожного коректного значення типу. Якщо об’єкт не повинен існувати з порожньою назвою або від’ємним значенням, перевірте це в одному визначеному місці:

```go
func NewRecord(name, category string, value float64) (Record, error) {
	name = strings.TrimSpace(name)
	if name == "" {
		return Record{}, errors.New("назва не може бути порожньою")
	}
	if value < 0 {
		return Record{}, errors.New("значення не може бути від'ємним")
	}
	return Record{Name: name, Category: category, Value: value}, nil
}
```

Конструктор у Go — звичайна функція, а не спеціальний синтаксис. Він корисний тоді, коли справді забезпечує правила створення.

## 6. Значення чи вказівник

Метод із отримувачем-значенням доречний, коли не змінює об’єкт і структура невелика. Вказівник потрібний, коли метод змінює стан або копіювання структури небажане. Не змішуйте обидва підходи без причини.

```go
func (r Record) IsValid() bool { /* ... */ return true }
func (r *Record) Rename(name string) error { /* ... */ return nil }
```

## 7. Функції колекційної логіки

Алгоритм зручно оформити як функцію, що приймає дані й повертає результат або помилку:

```go
func Filter(records []domain.Record, minimum float64) []domain.Record
func Summary(records []domain.Record) (Result, error)
```

Продумайте, чи має функція змінювати вхідний зріз. Якщо сортування не повинно змінювати дані виклику, зробіть копію та зафіксуйте це в назві, документації або тесті.

## 8. Консольний пакет

Функції консолі мають працювати з абстракціями `io.Reader` та `io.Writer`, а не напряму з глобальними `os.Stdin` і `os.Stdout`:

```go
func ReadRecords(reader io.Reader) ([]domain.Record, error)
func PrintSummary(writer io.Writer, result analysis.Result) error
```

Такі функції можна перевірити через `strings.NewReader` і `bytes.Buffer`. Саме в цьому пакеті доречні таблиці, кольори та інші елементи оформлення. Предметні пакети не повинні знати про ANSI-коди.

## 9. Імпорти та видимість

Ідентифікатор із великої літери експортується з пакета, з малої — лишається внутрішнім. Експортуйте лише те, що потрібно іншим пакетам. Якщо виник циклічний імпорт, це сигнал переглянути межі відповідальності; Go не дозволяє цикли імпортів.

Назва пакета описує його призначення і зазвичай є коротким іменником. Уникайте загальних назв `utils`, `helpers`, `common`, доки не можете чітко назвати спільну відповідальність.

## 10. Порядок рефакторингу

1. Зафіксуйте поточну працездатну версію тестами й коммітом.
2. Визначте незалежну предметну функцію.
3. Перемістіть її та відповідні типи в пакет.
4. Виправте імпорти й запустіть `go test ./...`.
5. Винесіть введення/виведення в окремий пакет.
6. Скоротіть `main` до складання компонентів.
7. Запустіть `gofmt`, `go test ./...` і `go vet ./...`.

Робіть невеликі кроки: тоді причина помилки видима в diff.

## Ознаки вдалої структури

- алгоритми можна тестувати без консолі;
- зміна оформлення не змінює предметну логіку;
- `main.go` легко прочитати зверху вниз;
- кожен пакет має зрозумілу одну головну відповідальність;
- помилки повертаються до рівня, який знає, як їх показати;
- немає глобального змінного стану без обґрунтування.

## Практика

Дослідіть приклад [`clean-main`](../../examples/clean-main/). Намалюйте схему залежностей власного проєкту й письмово поясніть кожну межу пакета. Після перенесення кожного блоку запускайте тести.
